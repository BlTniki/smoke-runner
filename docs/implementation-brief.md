# Технические рамки реализации

Статус: согласованные рамки, версия 1.2

Документ фиксирует ограничения и качества системы, но намеренно не выбирает
Telegram-фреймворк, библиотеку графиков или ORM.

## 1. Зафиксированные предпочтения

- язык: Python;
- база: SQLite;
- получение Telegram updates: long polling;
- размещение: личный VPS;
- первая версия: несколько приглашённых пользователей с раздельными данными;
- желательно контейнерное развёртывание;
- разработка должна оставаться возможной на рабочем ноутбуке без Docker.

## 2. Рекомендуемая форма системы

Для MVP достаточно одного процесса и одной базы. Логические части нужно отделить
друг от друга, даже если они работают в одном приложении:

```text
Telegram handlers
       |
Application use cases
       |
Domain rules: intervals, wake cycles, metrics
       |
SQLite repositories

Scheduler -> milestone/report use cases -> Telegram delivery

Optional AI commentary port -> external agent (future)
```

Правила расчёта должны быть обычными Python-функциями без зависимости от
Telegram и SQLite. Это позволит доказать корректность тестами и не дублировать
формулы между экраном и отчётами.

## 3. Концептуальная модель данных

Минимально потребуются следующие сущности; точная схема выбирается на этапе
дизайна реализации.

- `smoking_events`: идентификатор, фактическое время, время создания, источник
  (`now`, `backfill`), владелец, Telegram update id.
- `wake_events`: идентификатор, владелец, фактическое время, время создания,
  источник.
- `users`: внутренний идентификатор, Telegram user ID, статус доступа и даты
  активации/отзыва.
- `invite_codes`: хэш одноразового кода, срок действия, автор и состояние
  использования.
- `interval_changes`: владелец, новое значение интервала и момент начала
  действия. В базе хранится нормализованная длительность, а не только выбранная
  пользователем единица.
- `user_settings`: часовой пояс, время отчётов, состояние уведомлений; новый
  пользователь начинает с целевого интервала 1 час.
- `milestone_deliveries`: пользователь, эпизод-основание и состояние отправки
  уведомления о рубеже.
- `report_deliveries`: тип и период отчёта, состояние/время доставки; уникальность
  по пользователю, типу и периоду защищает от дублей.
- `dashboard_state`: идентификатор текущего сообщения и конец активного окна.
- `schema_migrations`: версия схемы базы.

Производные метрики не являются первичным фактом. Их следует рассчитывать из
событий и истории настроек либо хранить только как пересоздаваемый кэш.

Все пользовательские таблицы содержат внутренний `user_id`. Репозитории и
application use cases требуют его явно; запросы без пользовательского контекста
разрешены только административным операциям.

## 4. Доступ и изоляция

Telegram уже удостоверяет user ID отправителя, а приглашение отвечает на вопрос,
кому разрешено пользоваться ботом. Рекомендуемый поток:

1. администратор создаёт случайный одноразовый код с ограниченным сроком жизни;
2. пользователь вводит его в личном чате или открывает start-ссылку;
3. сервер сравнивает код с безопасно сохранённым хэшем и атомарно помечает его
   использованным;
4. Telegram user ID привязывается к новому внутреннему пользователю;
5. дальнейшие запросы авторизуются по этой привязке без повторного секрета.

Один общий постоянный пароль не рекомендуется: его нельзя отозвать у одного
человека и легко переслать. Для маленького круга пользователей одноразовые коды
дают почти такой же простой UX без этих недостатков.

Бот принимает продуктовые команды только из private chat. Callback-кнопки не
содержат доверенный `user_id`: владелец ресурса определяется по отправителю и
проверяется сервером. Код приглашения не пишется в application logs.

## 5. Надёжность

- Запись события и регистрация обработанного Telegram update выполняются одной
  транзакцией.
- Для SQLite включаются foreign keys и режим, подходящий одному пишущему процессу
  с параллельным чтением; конкретные настройки подтверждаются нагрузочным тестом.
- Одновременно запускается ровно один polling-процесс, если не реализована
  координация экземпляров.
- Отправка отчёта должна переживать сбой между генерацией и Telegram API. Нужна
  идемпотентная запись состояния с безопасным повтором.
- То же правило применяется к уведомлению о достижении рубежа; новая сессия
  инвалидирует старую ещё не отправленную задачу.
- Логи структурированы и не содержат bot token.
- На VPS настроены проверка живости процесса и автоматический перезапуск.

## 6. Резервное копирование

Контейнер сам по себе не является резервной копией. Файл SQLite хранится во
внешнем volume/каталоге VPS. Нужны:

1. согласованный snapshot SQLite, а не простое копирование потенциально
   изменяемых файлов;
2. ежедневная копия вне каталога приложения;
3. ограничение срока хранения;
4. периодическая проверка восстановления на отдельном временном файле.

Точные команды и место хранения должны появиться в runbook до запуска.

## 7. Разработка без Docker на рабочем ноутбуке

Контейнер не обязан быть локальной средой разработки. Практичный путь:

- запускать приложение и тесты в обычном Python virtual environment;
- использовать временную SQLite-базу для тестов;
- держать Dockerfile как способ упаковки для VPS;
- собирать образ на личном компьютере, VPS или в CI, а не на рабочем ноутбуке.

Запасной путь — вообще не использовать контейнер на первом этапе и запускать
virtual environment через `systemd`. Выбор способа доставки не должен менять код
приложения или расположение постоянных данных.

## 8. Обновление таймера в Telegram

Обычное сообщение Telegram не исполняет клиентский код. «Живой» обратный отсчёт
означает частое редактирование сообщения ботом, даже когда пользователь на него
не смотрит. Это создаёт лишний трафик, фоновые задачи и риск ограничений API.

Решение для MVP: у пользователя есть одно сообщение-дашборд. После его открытия
или ручного обновления планировщик редактирует сообщение раз в 5 минут в течение
30 минут. Каждое действие и наступление рубежа обновляют его немедленно. Затем
обновления прекращаются до следующего взаимодействия.

Так одна сессия просмотра создаёт не более шести фоновых редактирований. Ручная
кнопка остаётся доступной постоянно. Состояние активного окна хранится в базе,
чтобы перезапуск не создавал несколько циклов обновления.

Если после использования станет понятно, что пяти минут недостаточно, отдельно
оценить:

- минутное обновление внутри ещё более короткого активного окна;
- Telegram Mini App с локальным таймером;
- иной формат без фоновых редактирований.

## 9. Точка расширения для AI-комментатора

Генератор отчёта должен сначала получить полностью готовую детерминированную
модель отчёта. После этого необязательный интерфейс `comment(summary)` сможет
вернуть текстовый блок или контролируемую ошибку.

В MVP допустима реализация-заглушка, всегда возвращающая «комментария нет», но
контракт входных данных фиксируется и тестируется. Внешний вызов в будущем должен
иметь короткий таймаут, ограничение длины ответа, версионированный prompt и
fallback на обычный отчёт. Провайдер AI не должен проникать в доменную логику.
Внешняя интеграция вызывается только для пользователей, явно включивших её в
настройках.

## 10. Проверка реализации

До развёртывания нужны как минимум:

- unit-тесты формул на границах интервала;
- табличные тесты сетки рубежей непосредственно до, на и после порога
  значительного опоздания;
- тест отсутствия накопленного сдвига после нескольких небольших опозданий;
- property-based или табличные тесты вставки задних событий и пересчёта;
- тесты границ дня/недели и смены часового пояса;
- тесты первого частичного недельного периода и воскресной границы;
- тесты серий, включая день без эпизодов и заднее исправление нарушения;
- тесты атрибуции фактического интервала к неделе завершающего эпизода;
- тесты последней сессии между двумя пробуждениями;
- тест идемпотентности повторного Telegram update;
- тесты одноразовости/истечения приглашений и отзыва доступа;
- тесты, доказывающие отсутствие доступа к данным другого пользователя;
- тесты отмены и однократной доставки уведомления о рубеже;
- тест ограничения активного таймера шестью фоновыми обновлениями;
- интеграционные тесты миграций SQLite;
- тест восстановления пропущенных отчётов после перезапуска;
- визуальная проверка графиков с нулями, пропусками и длинной историей;
- ручной smoke test на отдельном тестовом боте.

## 11. Предлагаемые этапы после согласования требований

1. Выбрать библиотеки и оформить короткие архитектурные решения.
2. Реализовать доменные правила и тесты без Telegram.
3. Добавить SQLite-схему, миграции и операции исправления истории.
4. Добавить Telegram-интерфейс, приглашения и проверку изоляции пользователей.
5. Добавить планировщик, уведомления, отчёты и графики.
6. Подготовить способы native- и container-запуска, backup/restore runbook.
7. Зафиксировать контракт будущего AI-комментатора без внешнего вызова.
8. Провести семидневный личный пилот и уточнить метрики по реальному использованию.
